# 画像永続化アーキテクチャ改善計画 (R2導入)

## 目的

エピソード/作品画像 (`Anime.imageUrl` / `Episode.imageUrl` / `UnidentifiedAnime.imageUrl` に保存されているプロバイダ側の元画像URL) を現在の「パススルー変換のみ・永続保存なし」から、Cloudflare R2 を使った永続化アーキテクチャへ改善するにあたっての設計方針・作業ステップ・優先度を整理する。**このドキュメントは計画のみであり、コード変更は含まない。**

advisor 2名 (Fable, Astra) に独立して検討させた結果を統合し、実装コードの現状 (`src/routes/img.ts`, `wrangler.toml`, `prisma/schema.prisma`) を実際に読んで裏付けを取った上でまとめる。

関連ドキュメント: [notification-recording-integrity-plan.md](notification-recording-integrity-plan.md) (同様の計画書フォーマット), CLAUDE.md (Lambda デプロイ節、Docker/AWS ハイブリッド構成の既存前例)。

---

## 0. 背景と全体像

### advisor 2名に独立検討させた経緯

「画像を永続保存すべきか、すべきなら Workers 継続か Docker (VPS 等) への移行かを含めて検討してほしい」という論点に対し、Fable と Astra の 2 名の advisor に**独立に**設計検討をさせた。両者はこのリポジトリの Lambda ハイブリッド構成 (JP/US IP 要件のためのスクレイピングだけを AWS Lambda に切り出す既存の前例) を参照した上で、画像永続化についても Workers から切り出す必要があるかを検討している。

### 結論の一致点

- 画像は永続保存すべきである (現状のパススルー変換 + 一時キャッシュの継続は不十分)。
- Cloudflare Workers 継続で十分。R2 バインディングを追加するだけで実現でき、**Docker 移行 (VPS 等への完全移行) は画像保存を理由にする限り不要**。想定データ量 (数百MB〜1GB程度、幅バリアント込みでも) は R2 無料枠 (10GB、egress $0) に収まり、コスト面でも VPS が有利になる余地はない。
- 最小変更設計として `img.ts` を read-through cache 化する: R2 hit なら即返却、miss なら現行の fetch + WASM 変換 → `waitUntil` で R2 へ put。キーは元 URL のハッシュ (例: SHA-256) + 幅パラメータから決定的に導出し、D1 スキーマ変更を避けられる。
- Lambda ハイブリッド構成の既存の前例は「Workers で原理的に不可能な制約 (JP/US 地理的 IP 要件)」が理由であり、画像保存にはそのような制約が存在しないため、Docker 移行の根拠にはならない。

> **注 (実測後)**: 両 advisor の「数百MB〜1GB」という見積もりは外れている。実測では現行方針 (元バイナリ込み) で **176.78 GiB / 月 $2.70**、WebP のみでも 10.26 GiB で無料枠を超える (後述の「実測結果」節)。ただし結論「Workers + R2 で十分、Docker 移行は不要」は変わらない — 月 $3 は VPS より安い。

### 結論の相違点 (両方を本計画に反映する)

| advisor | 永続保存すべき対象 | 理由 |
|---|---|---|
| **Fable** | 変換済み WebP | CPU 課金削減。WASM 変換を「1 画像 1 回」に固定できる |
| **Astra** | 元バイナリ | 配信終了後、プロバイダ CDN の元画像 URL が 404 になり二度と取得できなくなるリスク (`AbemaKeyArchive` と同種の「後で取れなくなるものを先に永続化する」思想)。WebP は元から再生成できる派生物であり優先度は低い |

両者の主張は排他ではなく両立する。本計画では **「元バイナリ + 変換済み WebP 派生物の両方を R2 に保存する」を統合方針として採用する** (詳細は 5 章)。

### Astra 独自の追加指摘

- Worker のメモリ制限 (128MB) により、`wasm-image-optimization` が大きな元画像でクラッシュしうる。現状 (`img.ts:30-32`) は変換失敗時に無言で 500 を返しているため、**既に一定数の変換が失敗している可能性がある**。R2 化に着手する前に、まず現状の失敗率を確認する調査タスクを先行させるべきという指摘 (4 章・6 章に反映)。
- Docker 移行の「唯一の本気の統合論拠」として、`sharp` (libvips) による画質・安定性向上と、`lambda/fetch` の JP/US IP 要件をコンテナに統合できないか検討したが、US IP 要件が残るため Lambda の完全解体はできず (JP VPS 1 台では要件を満たせない)、コンポーネント数は実質減らないため却下した、という検討過程を経ている。ただし「将来 US IP 要件自体を捨てられると判断できた場合」は、画像とは別の理由 (Lambda + ECR + Terraform の解体) で JP VPS への統合を検討する価値がある、という将来的な留保を残す。

### `[placement] region` の妥当性見直し (両 advisor 一致の指摘)

両 advisor が独立に、`wrangler.toml:8-9` の `[placement] region = "aws:us-east-1"` により Worker が単一リージョン実行に固定されており、「Workers はグローバルエッジで速い」という前提がこのリポジトリでは既に成立していないことを指摘した。画像アーキテクチャとは独立した既存設定だが、日本のユーザーが主であれば画像配信レイテンシにも影響するため、本計画のスコープ外の別タスクとして 8 章で触れる。

## 1. 現状分析

### `img.ts` の処理フロー (`src/routes/img.ts`, 全43行)

- ルート定義: `app.get('/:key{.+}', ...)` (`img.ts:9`)。`src/index.ts:36` で `app.route('/api/img', imgRoutes)` としてマウントされているため、実際の URL は `/api/img/:key` (`?w=` クエリ対応)。呼び出し元は `src/app/components/proxy-image.tsx:30` の `ProxyImage` コンポーネントで、`src` (元画像URL) を base64url エンコードして `key` に埋め込む。
- キー復号: `key` の `-`/`_` を `+`/`/` に戻しパディングを補って `atob()` するだけ (`img.ts:10-13`)。ハッシュ化や正規化は一切行われておらず、**同一画像でも `w` パラメータが異なれば別キャッシュエントリになる** (`hono/cache` レベルでも R2 レベルでも同様の設計になる想定)。
- 幅パラメータ: `w` クエリを `parseInt` し、`1` 以上かつ有限なら `Math.min(w, 4096)` にクランプ (`img.ts:15-17`)。上限なしで任意の幅を要求できる (4096 まで)。
- エッジ一時キャッシュ: `app.use('/:key{.+}', cache({ cacheName: 'img-proxy', cacheControl: 'public, max-age=31536000, immutable' }))` (`img.ts:7`)。これは **Cloudflare Cache API によるエッジの一時キャッシュ**であり、永続ストレージではない (退去/パージされうる、かつ D1/R2 のような明示的な管理対象ではない)。
- 元画像取得: `fetch(url)` (`img.ts:19`)。`res.ok` でなければ 502 (`img.ts:20`)。`content-type` が `image/` で始まらなければ 502 (`img.ts:22-23`)。**画像バイナリはこの時点でも永続化されず、リクエストごとにオリジンへ fetch し直す**。
- WASM変換: `optimizeImage({ image, format: 'webp', width, quality: 80 })` (`img.ts:29`, `wasm-image-optimization/workerd`, `package.json:68` で `^2.0.11` を使用)。
- **変換失敗時の挙動 (実際に確認)**: `catch` ブロックは `return c.text('Optimization failed', 500)` のみで (`img.ts:30-32`)、`logger` や `console.error` 等の呼び出しは一切ない。失敗理由 (メモリ超過・不正な画像データ等) を判別する手段がコード上に存在せず、**発生していても検知できない構造**になっている。
- 成功時は変換済み WebP を `content-type: image/webp` + 同じ `cache-control` ヘッダーで返す (`img.ts:34-39`)。

### D1 のメタデータ管理 (`prisma/schema.prisma`)

- `Anime.imageUrl` (`schema.prisma:19`, `String` 必須)、`Episode.imageUrl` (`schema.prisma:66`, `String` 必須)、`UnidentifiedAnime.imageUrl` (`schema.prisma:110`, `String?` 任意) はいずれも**プロバイダ側の元URL文字列のみ**を保持し、画像バイナリは D1 に一切保存されていない。
- `AbemaKeyArchive` (`schema.prisma:79-99`) は、モデル直前のコメント (`schema.prisma:79-82`) に「無料配信中の license POST で得た AES-128 content key と segment URL を永続化しておくと、後で license endpoint を呼べずに再復号できる」と明記されており、**「配信終了後に取得不可能になるものを、取得可能なうちに先に永続化する」**という設計思想の直接の前例として参照できる。画像アーカイブも同種のリスク (配信終了後に元URLが 404 になる) を持つため、この前例をそのまま踏襲できる。

### `wrangler.toml` のバインディング状況

- KV (`wrangler.toml:27-29`, `[[env.staging/production.kv_namespaces]]`)・D1 (`wrangler.toml:31-36`)・Queues (`wrangler.toml:45-54`)・静的アセット (`wrangler.toml:17-20`) はバインド済みだが、**`r2_buckets` の定義はファイル全体 (共通設定・staging・production の全ブロック) に存在しない** (`grep` で確認済み、0件)。R2 を使うには新規にバインディングを追加する必要がある。
- `[placement] region = "aws:us-east-1"` (`wrangler.toml:8-9`) が共通設定に定義されており、`[env.staging]` / `[env.production]` にも上書きがないため、staging・production 双方の Worker 実行がこの設定を継承し米国東部リージョンに固定される。

## 2. 問題点

- **配信終了後のサムネイル消失リスク**: 画像バイナリを一切永続化していないため、プロバイダが配信を終了し元画像URLが 404 を返すようになった時点で、その作品/エピソードのサムネイルは二度と取得できなくなる。録画管理アプリという性質上、配信終了後こそサムネイルの参照価値が高まる (視聴済み作品の履歴として) ため、このリスクは実害が大きい。
- **WASM変換のメモリ制限とサイレント失敗の可能性**: Worker のメモリ制限 (128MB) の下で `optimizeImage()` が大きな元画像に対してクラッシュしうるが、`img.ts:30-32` の `catch` はログを一切出さずに 500 を返すのみで、失敗の発生自体を運用側が検知する手段がない。R2 化に着手する前に、この失敗率を可視化する調査を先行させるべき。
- **`[placement] region` によるレイテンシ問題**: `wrangler.toml:8-9` の設定により Worker 実行が米国東部に固定されており、「Workers はグローバルエッジで実行される」という前提が崩れている。日本のユーザーが主であれば、画像配信を含む全リクエストが太平洋往復のレイテンシを負う (エッジキャッシュヒット時でも Worker 自体の実行が固定リージョンで行われる)。

## 3. 設計方針 (比較)

### 3.1 実行基盤: Workers継続 + R2 vs Docker移行

| 案 | 内容 | メリット | デメリット・コスト |
|---|---|---|---|
| **案A: Workers継続 + R2バインディング追加 (推奨)** | `wrangler.toml` に `[[r2_buckets]]` を追加し、`img.ts` を read-through cache 化する。既存の Hono ルーティング・OpenAPI 構成・デプロイフローをそのまま維持する。 | 実装コストが最小 (既存ファイルの拡張のみ)。想定データ量 (数百MB〜1GB程度) は R2 無料枠 (10GB、egress $0) に収まり追加コストが実質ゼロ。CLAUDE.md の既存デプロイ・環境変数運用をそのまま使える。 | Worker のメモリ制限 (128MB) による WASM 変換失敗のリスクは残る (別途調査・対処が必要、2章参照)。 |
| 案B: Docker移行 (VPS等への完全移行) | 画像取得・変換・配信を VPS 上の Docker コンテナ (例: `sharp` を使った Node.js サーバー) に移行する。 | `sharp` (libvips) は `wasm-image-optimization` よりメモリ効率・画質で安定している可能性がある。 | 画像保存だけを理由にした移行は過剰スコープ (R2 追加だけで永続化は実現できる)。`lambda/fetch` の JP/US IP 要件はコンテナに統合してもUS IP要件が残り Lambda を解体できないため、コンポーネント数は実質減らない (Astra の検討過程で却下)。VPS 運用コスト・監視・デプロイパイプラインを新規に持つ必要があり、R2 案よりトータルコストが高い。 |

**結論**: **案A (Workers継続 + R2) を採用する**。画像永続化を理由にした Docker 移行は不要。将来 `lambda/fetch` の US IP 要件自体を不要と判断できた場合は、画像とは別の理由 (Lambda + ECR + Terraform 構成の解体) で JP VPS への統合を検討する余地を残すが、これは本計画のスコープ外。

### 3.2 保存対象: 元バイナリ vs WebP派生物 vs 両方

| 案 | 内容 | メリット | デメリット・コスト |
|---|---|---|---|
| 案1: 元バイナリのみ保存 (Astra案) | オリジンから取得した元画像バイナリのみを R2 に保存し、WebP変換は毎回リクエスト時に実行する。 | アーカイブ性を担保できる (配信終了後も元画像は残る)。実装がシンプル (書き込み経路が1つ)。 | WASM変換のCPU課金は削減されない。同一画像・同一幅への繰り返しリクエストで毎回変換コストが発生する。 |
| 案2: 変換済みWebPのみ保存 (Fable案) | WASM変換後のWebPのみをキー (元URLハッシュ + 幅) ごとに R2 に保存し、元バイナリは保存しない。 | CPU課金を削減できる (同一キーへの変換は1回のみ)。 | 配信終了後に元画像URLが404になった場合、まだキャッシュされていない幅バリアント (例: 新しいレスポンシブブレークポイント) を後から生成できなくなる。アーカイブ性の担保という点で不十分。 |
| **案3: 両方保存 (推奨)** | 元バイナリを幅無関係の1エントリとして保存し、WebP変換結果を幅ごとに別エントリとして保存する。read-through cache は WebP キー優先で参照し、miss時は「R2の元バイナリ (あれば) → なければオリジンfetch」→ 変換 → 両方をR2に反映する。 | アーカイブ性 (元バイナリ) とCPU課金削減 (WebP再利用) を両立できる。配信終了後でも新しい幅バリアントを元バイナリから再生成できる。 | 保存対象が2種類になるためR2キー設計・書き込みロジックがやや複雑になる (案1・2に比べ実装コストは増えるが、両者の利点を両立するために必要な差分)。 |

**結論**: **案3 (両方保存) を統合方針として採用する**。Fable (CPU課金削減) と Astra (アーカイブ性) の主張は排他ではなく両立するため、双方の目的を満たす設計とする。

## 4. 実装ステップ

- [x] `img.ts:30-32` の変換失敗 (`catch` ブロック) にログ出力を追加し、実際の失敗率を計測する調査タスクを先行実施する (R2化着手前の前提調査、Astra指摘)
- [x] `wrangler.toml` に `[[r2_buckets]]` を追加する (共通設定・`[env.staging]`・`[env.production]` の各ブロックに、staging/production 用の別バケットをバインド)
- [x] R2キーの導出方式を決定する: 元URLのSHA-256ハッシュを基底キーとし、元バイナリは `<hash>/original`、WebP変換結果は `<hash>/<width>.webp` のように幅ごとに分離する案を軸に検討する (D1スキーマ変更は不要、`imageUrl` はそのまま元URL文字列を保持し続ける)
- [x] 元画像アーカイブ経路を実装する: `img.ts` のオリジンfetch (`img.ts:19`) 成功時に、`waitUntil()` で元バイナリをR2の `<hash>/original` へ保存する (未保存の場合のみ)
- [x] `img.ts` を read-through cache 化する: リクエスト時にまず R2 の `<hash>/<width>.webp` を参照し、hit なら即返却 (現在の `hono/cache` によるエッジ一時キャッシュに加えてR2を永続層として併用)。miss の場合は R2 の `<hash>/original` を参照し、あればそれを変換に使い (オリジンfetchをスキップ)、なければ現行のオリジンfetchを行う
- [x] 変換成功時、`waitUntil()` でWebP変換結果を R2 の `<hash>/<width>.webp` へ保存する
- [x] 既存の `hono/cache` によるエッジ一時キャッシュ (`img.ts:7`) は変更せずそのまま併用する (R2はパージされない永続層、Cache APIは高速なエッジ一時層という役割分担を維持する)
- [ ] 上記変更後、`img.ts` の変換失敗率が調査タスクの計測結果からどの程度改善するかを確認する (R2ヒット時は変換自体が発生しないため、失敗率自体が下がるはず)

### 実装時に確定した仕様 (上記の案からの変更点)

実装にあたり、計画時点では未決だった以下の3点を確定させた。いずれも既存資産との整合を優先した結果、計画書の案から変更している。

**キー導出は SHA-256 ではなく既存 `imageKey()` の UUIDv5 を採用した。**
リポジトリには既に `src/lib/image-key.ts` の `imageKey(url)` があり、元URLから UUIDv5 で `<uuid>.webp` を決定的に導出している。さらに `scripts/fetch/common/upload_images.sh` は fixtures の画像を cwebp で変換し、**まさにこのキーで R2 に一括投入する**ように書かれている。SHA-256 で新たに切ると、このバッチと Worker がそれぞれ別のキー体系で同じ画像を二重に持つことになる。そこで `imageBaseKey(url)` (= `<uuid>`) を基底キーとし、以下を導出する。

| 対象 | キー |
|---|---|
| 原寸 WebP | `<uuid>.webp` (= 既存 `imageKey()` と同一。バッチ投入分がそのまま hit する) |
| 幅指定 WebP | `<uuid>/w<width>.webp` |
| 変換前の元バイナリ | `<uuid>/original` |

`imageKey()` のシグネチャと戻り値は変更していない (`scripts/fetch/common/list_image_urls.ts` が依存しているため)。

**バケットは staging / production で共用する (`nagisa-images`)。**
画像は元URL由来の不変コンテンツで環境差がなく、キーが決定論的なので環境間で衝突しない。計画書の「staging/production 用の別バケット」からは変更している。

なお `nagisa-images` は過去にも存在していた。`39250c8` (2026-03-29) で R2 対応を入れた際に 3 ブロック全てにバインドされ、取り込み時に画像をアップロードしていたが、`8e02eda` (2026-05-05) の「Also remove deleted R2 bucket binding that was preventing deploys.」の時点でバケットは既に削除済みで、デプロイを通すためにバインドだけが剥がされていた。誰がなぜ消したかは記録に残っていない。今回 `wrangler r2 bucket create nagisa-images` で作り直している (2026-09-21、作成直後は 0 オブジェクト)。

**容量の実測は `scripts/analysis/` に置いた。**
`import-d1-dump.ts` (staging のダンプをローカル miniflare D1 へ) → `dump-image-urls.ts` (→ `.cache/image-urls.tsv`) → `image-size-audit.ts` (原寸サイズを HEAD で実測) → `webp-matrix.ts` (品質×解像度の総当たり変換) → `webp-matrix-report.ts` (方針別のコスト集計) の順に流す。中間生成物は `.cache/` (gitignore 済み)。`image-convert-sample.ts` / `convert-report.ts` は q80 固定の旧版で、`webp-matrix*` に置き換わっている。

取り込み前のローカル miniflare D1 は staging の 4.4% しか持たないので、母数には使えない。`wrangler d1 export anime-tracker-staging --remote` で 567 MB のダンプを落とし、`import-d1-dump.ts` でローカルへ流し込んだ (anime 11,943 / episodes 260,328 / seasons 14,966 / unidentified_anime 4,278、画像 URL 229,144 件がリモートと完全一致)。以後 `dump-image-urls.ts` は既定で `local` を読む。

**geo ブロックされたホストは SOCKS5 プロキシ経由で取る。**
Crunchyroll は日本の IP から取得できないため、`.devcontainer/compose.yaml` に WireGuard (`vpn`) と、そのネットワーク名前空間に同居する SOCKS5 プロキシ (`proxy`) を追加した。プロキシの待ち受けは netns を共有する都合で `vpn:1080` になる。`scripts/analysis/lib/fetch-via.ts` がこの差異を吸収し、`ANALYSIS_PROXY_HOSTS` に挙げたホストだけを curl 経由に切り替える (Bun の `fetch` は `socks5://` を受け付けず `UnsupportedProxyProtocol` になるため)。

geo ブロックは 301 ではなく **200 + 281,341 バイトのエラーページ HTML** で返るため、content-length だけを見ると画像として数えてしまう。`probeSize()` は content-type が `image/` で始まらない応答の `bytes` を null にする。加えて Crunchyroll の imgsrv は HEAD に content-length を返さず Range も無視して 200 で全 body を返すので、このホストだけは本体を落としてバイト数を数えている。

#### 実測結果 (2026-09-21 / 元バイナリ全件は 2026-09-22)

母数はコーパス全体 229,144 URL。**元バイナリは全件をダウンロードして実測した。WebP 側だけが標本推定である。**

- 原寸サイズ: 229,144 件すべてを `.cache/originals/` に落として実測 (`download-originals.ts`)。成功 229,140 件、失敗 4 件 (0.0017%)。
- WebP サイズ: 各ホスト 40 枚をサイズ順の等間隔で抜き、Worker と同じ `wasm-image-optimization` で 5 品質 × 9 幅 = 45 通りに変換して計測 (計 7,200 変換)。

**Crunchyroll をようやく計測できた。** 全 URL が `/imgsrv/display/thumbnail/1920x1080/` 固定で、オリジンが常に 1920×1080 に描き直して返すため原寸は平均 636 KiB。旧版が代用していた加重平均 511 KiB は 25% の過小評価だった。

- 404: `/build/assets/img/default-poster.png`
- 500: `/imgsrv/display/thumbnail/1920x1080/catalog/crunchyroll/{b2df7205…, 2d71c5c3…, 0e912fd0…}.jpg`

##### 旧版の外挿値は外れていた

旧版はこの欄に **162.61 GiB** と書き、「rowid 順の等間隔抽出なので偏りは小さく、95% 信頼区間は 159.8〜165.4 GiB (±1.7%、有限母集団修正込み)」と付記していた。**実測 144.76 GiB はこの区間に入らない。外挿は 12.3% の過大評価だった。**

信頼区間が外れた以上、原因は標本誤差ではなく抽出の偏りである。最も大きいのは hjholdings で、標本平均 1,931 KiB に対し全件平均は 1,718 KiB (11% 過大)。HEAD の content-length が取れた URL だけが標本に残るため、**大きい画像ほど残りやすい方向の選択効果**が働いたとみられる。

一方、旧版が「過小評価の恐れがある」と名指しした Crunchyroll (外挿 28.53 GiB) は実測 28.31 GiB で、0.8% しかずれていなかった。**警戒すべきホストの見立て自体が逆だった。**

##### 保存方針 × 品質 の総容量と月額

月額は 10 GB 無料枠を差し引いた後、$0.015/GB-月 (R2 は egress 無料)。「配信5幅」は当時の `PERSISTED_WIDTHS` すなわち 176/200/400/480/800 で、全画像に 5 幅すべてが要求される最悪ケース (この 5 幅は後述の通り 3 段に集約した)。

| 方針 | q50 | q60 | q70 | **q80** (現行) | q90 |
|---|---:|---:|---:|---:|---:|
| P1. 配信5幅のみ | 9.66 GiB / $0.01 | 10.69 GiB / $0.02 | 11.84 GiB / $0.04 | **14.77 GiB / $0.09** | 22.62 GiB / $0.21 |
| P2. 配信5幅 + w960 | 14.36 GiB / $0.08 | 15.93 GiB / $0.11 | 17.69 GiB / $0.13 | **22.25 GiB / $0.21** | 34.82 GiB / $0.41 |
| P3. 配信5幅 + w1280 | 16.03 GiB / $0.11 | 17.78 GiB / $0.14 | 19.75 GiB / $0.17 | **24.91 GiB / $0.25** | 39.41 GiB / $0.48 |
| P4. 配信5幅 + 原寸WebP (=案2) | 20.24 GiB / $0.18 | 22.50 GiB / $0.21 | 25.08 GiB / $0.25 | **32.02 GiB / $0.37** | 52.29 GiB / $0.69 |
| **P5. + 元バイナリ (=案3, 現行実装)** | 165.00 GiB / $2.51 | 167.26 GiB / $2.54 | 169.84 GiB / $2.59 | **176.78 GiB / $2.70** | 197.05 GiB / $3.02 |

読み取れること:

- **元バイナリが支配的**。P5 の 176.78 GiB のうち 144.76 GiB (82%) は元バイナリで、品質を振っても動かない。P5 のセル間で月額が $2.51〜$3.02 にしか散らないのはこのため。**品質・解像度の選択は元バイナリを保存する限りコストにほとんど影響しない。**
- **品質の効きは非線形**。q80 → q70 で WebP 側が 20% 減るのに対し、q80 → q90 は 53% 増える。q90 は容量あたりの見返りが悪い。
- **WebP だけなら実質無料枠内**。無料枠の 10 GB は 10 進なので 9.31 GiB に相当し、P1 は q50 (9.66 GiB) でもわずかに超える。ただし超過は月 $0.01〜$0.02 で、q80 でも $0.09。P4 でも q80 で月 $0.37。
- **月額よりも初期書き込みの方が高い**。全 229,144 件を一度に埋めると Class A は P1 で 1,145,720 操作 = $5.16、P5 で 1,604,008 操作 = $7.22。read-through で埋まる分には都度課金なので一括投入しない限り顕在化しない。

##### 元バイナリをローカルに逃がす場合 (P6)

**元バイナリの保管先を R2 からローカル (手元のディスク) に移すなら、R2 側の原寸 WebP も不要になる。** 任意の幅を作り直す元としてはローカルの元バイナリが上位互換で (再変換の劣化が乗らない)、R2 の原寸 WebP は劣化した二重の保険にしかならないため。

以下は幅ラダーを集約する前 (5 幅) の数字。3 段に絞った現在は配信幅ぶんが 14.77 → 10.26 GiB に下がるだけで、大小関係は変わらない。

| 配信5幅 | 原寸 WebP | 総容量 | 月額 |
|---|---|---:|---:|
| q80 | q80 | 32.02 GiB | $0.37 |
| q80 | q90 | 44.44 GiB | $0.57 |
| q70 | q80 | 29.08 GiB | $0.32 |
| **q80** | **持たない (= P6)** | **14.77 GiB** | **$0.09** |

P5 の $2.70 に対し **$0.09 (97% 減)**。ローカル側には元バイナリ 144.76 GiB を置くことになる。

ただし現行コードのままでは移行できない。前提が 2 つ崩れる:

1. **再生成元の差し替えが要る。** `img.ts` は miss 時に `originalKey(url)` を引いて変換元にしている (step 2)。原寸を置かないとこの読み取りは常に空振りするので、`getObject` と `putObject` の両方を削除する (残すと miss ごとに無駄な Class B が 1 回増える)。
2. **「一度触れば全幅を作れる」が成立しなくなる。** read-through なので R2 に入るのは実際にリクエストされた幅だけ。今は元バイナリが R2 にあることでこの性質が担保されているが、外すと w400 だけ要求された画像は w800 が未生成のまま残り、その後オリジンが 404 になると作れない。
   - さらに step 3 の条件は `width === undefined || PERSISTED_WIDTHS.has(width)` であり、**原寸 WebP が書かれるのは `?w=` 無しで来たときだけ**。`ProxyImage` は常に width を渡すため、実運用では原寸 WebP はほぼ書かれていない。つまり「P4 に移行する」つもりでも、コードを変えなければ再生成元が何も残らない。
   - 対処は miss 時にラダーの全段をまとめて生成・保存する (現行 3 段なら変換 3 回 / put 3 回。容量は 10.26 GiB のまま)。幅リストを変えたときだけローカルから一括再投入すればよい。

ローカルへの一括ダウンロードは **実施済み** (229,140 件 / 144.76 GiB、`.cache/originals/`)。Crunchyroll 分はプロキシ経由で取得した。

##### 判断

**元バイナリを R2 に置き続けるなら、現行の P5 (案3) / q80 を維持する。** 月 $2.70 は、配信終了後に元画像が 404 になっても任意の幅を再生成できるアーカイブ性の対価として妥当。品質を落としても元バイナリが 82% を占める以上、削減幅は月 $0.2 未満にしかならず、画質を犠牲にする理由がない。

**元バイナリをローカルに逃がす方針を採るなら P6 (配信5幅 q80 のみ / $0.09)。** 中間の P4 (原寸 WebP を R2 に残す / $0.37〜$0.57) は、ローカルに元バイナリがある限り劣化した重複でしかないので採らない。この場合に限り上記 2 点の実装変更が前提になる。

**幅バリアントの書き込みは許可リストに限定する。**
`?w=` は 1〜4096 の任意値を受け付けるため、素直に幅ごと保存すると 1 画像あたり最大 4096 オブジェクトまで外部から膨らませられる (クラスA操作とストレージの増加)。フロントの `ProxyImage` が使う幅だけを `img.ts` の `PERSISTED_WIDTHS` に置き、この集合と「幅なし」だけを永続化対象とした。**許可リスト外の幅も従来どおり変換して返す**ため、レスポンスの内容は現行と変わらない。

##### 幅ラダーを 5 段から 3 段に集約した (2026-09-22)

旧 5 幅 (176/200/400/480/800) は刻みすぎだった。q80 での 1 枚あたり加重平均は 176→4.8 KiB / 200→5.5 KiB / 400→13.0 KiB / 480→15.8 KiB / 800→28.4 KiB で、**176 と 200 の差は 0.7 KiB、400 と 480 の差は 2.8 KiB** しかない。隣り合う段を分ける意味がないので、DPR 1/2/3 の境界に合わせて **200 / 400 / 800 の 3 段**に集約した。

| ラダー | 総容量 | 月額 | 一括投入時の Class A |
|---|---:|---:|---:|
| w800 のみ | 6.20 GiB | $0.00 | $1.03 |
| 400 + 800 | 9.05 GiB | $0.00 | $2.06 |
| **200 / 400 / 800 (採用)** | **10.26 GiB** | **$0.02** | **$3.09** |
| 200 / 400 / 800 / 1280 | 20.40 GiB | $0.18 | $4.12 |
| 旧 5 幅 | 14.77 GiB | $0.09 | $5.16 |

**1 幅だけでも R2 の請求はほぼ変わらない** (w800 のみ 6.20 GiB と 3 段 10.26 GiB の差は月 $0.02)。3 段にする理由は請求書ではなく**閲覧者の転送量**で、76px の枠に 800px を配る場合と 200px を配る場合で 1 枚あたり 23 KiB 違う。一覧に 40 枚並ぶ画面では 1 MB 近い差になる。

1280 の追加は見送った。+10 GiB / +月 $0.16 は許容範囲だが、DPR3 端末で hero をどこまで見せるかという画質側の判断であり、今のところ必要性が確認できていない。

幅の選択は `ProxyImage` が一手に引き受ける。呼び出し側は**取得幅ではなく表示枠の CSS ピクセル幅** (`slotWidth`) を宣言し、`ProxyImage` が DPR 1/2/3 に必要な実ピクセル数を掛けてラダーの段へ丸め、`srcSet` に `1x/2x/3x` として並べる。`LADDER` と `PERSISTED_WIDTHS` は同じ値でなければならない (ずれた幅は「変換はするが保存しない」状態になり、毎リクエストでオリジン取得と変換が走る)。

##### 計測中に判明したこと

- **`wasm-image-optimization` は原寸より大きい幅を要求すると拡大する。** 縮小専用ではない。引き伸ばしても情報は増えずバイト数と変換時間だけ増えるため、`img.ts` で `result.originalWidth < width` を検出したら幅指定なしで焼き直すようにした。`scripts/analysis/lib/webp-axes.ts` の `outWidth` にあった「原寸より大きい幅を要求しても拡大されない」という注記は誤りである。
- **原寸が 1280px 未満の画像が 27〜33% ある** (Amazon 27% / hjholdings 33%)。「720p 上限に揃える」といった方針は、そもそも母集団の 1/3 に対して適用できない。

なお R2 の `get` / `put` は try/catch で握り、バインディング未設定や R2 障害時は warning ログを出して従来のパススルー経路 (オリジン fetch + 変換) にフォールバックする。R2 の不調でサムネイルが表示されなくなることはない。

## 5. 優先度・依存関係

- **優先度: 中〜高**。配信終了後のサムネイル消失リスクは実害が発生してから気づく類のバグであり、早期に着手する価値がある。ただし緊急のユーザー影響 (機能停止等) ではないため最優先ではない。
- **依存**: 変換失敗率の調査タスク (4章1項目目) は他のステップに依存せず単独で着手できるため、最初に実施する。この調査結果次第で、WASM変換のメモリ問題への対処 (例: 変換前に画像サイズを事前チェックして極端に大きい画像はスキップする等) を本計画に追加すべきか判断する。
- **依存**: R2バインディング追加 (4章2項目目) が完了しないと、以降のアーカイブ経路実装・read-through cache化は着手できない。
- 元画像アーカイブ経路とWebP read-through cache化は、同じ `img.ts` への変更のため同一PRでまとめて実装するのが自然 (別々のPRに分けると同じ関数に2回手を入れることになり非効率)。

## 6. 別途提起する既存設定の見直し

`wrangler.toml:8-9` の `[placement] region = "aws:us-east-1"` は、本計画 (画像永続化) とは独立した既存設定だが、両advisorが独立に「Workerの単一リージョン実行固定によりグローバルエッジという前提が崩れている」ことを指摘した。日本のユーザーが主であれば、画像配信を含む全リクエストのレイテンシに影響するため、**本計画のスコープ外の別タスクとして、この設定が現在も必要か (どのような経緯で `aws:us-east-1` に固定されたか) を見直すことを提起する**。R2バケット自体はリージョンを問わず自動でエッジに分散されるため、この見直しはR2導入の前提条件ではなく、並行して検討可能な独立タスクである。
